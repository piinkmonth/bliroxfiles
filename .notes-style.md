# notes style

the comments in this codebase are written the way i actually talk, not like
technical documentation. if you open a PR, match the voice. its genuinely not hard.

## the voice

1. **lowercase.** the only exceptions: SHOUT one word when its a real warning
   (NEVER, PLEASE, DONT, THIS), and keep real identifiers as they are: SQLite,
   AES-GCM, HTTP/1.1, CSP, IV, SHA-256, PBKDF2, the BLIROX_ env vars, type names,
   all that.
2. **casual and blunt.** contractions and slang are good: yeah, so, basically,
   lowkey, ngl, tbh, kinda, u, bc, "the thing that does X". mild swearing is fine
   if its natural (shit, damn, hell), sparingly. no slurs, ever.
3. **short.** most comments are one or two lines. only go longer when theres a
   real gotcha or a load-bearing reason someone has to know before they touch it.
4. **say WHY, not what.** the code already says what it does. the comment is for
   the reason it does it this way, or the trap you hit if you change it.
5. **no em dashes.** use a comma, a period, or parentheses instead. reads more
   human.
6. **keep the fact, keep the warning.** you can make a security note shorter, you
   cant make it quieter. never delete the reason a thing is dangerous.

## dont touch

- **code.** comments only. no renames, no logic changes, no reflowing real code.
- **UI labels.** in .tsx files you may delete a standalone preachy sentence that
  adds nothing. never touch a button label, a form label, an error message, or an
  instruction, those are functional.
